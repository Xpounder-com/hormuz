# Hormuz security posture

Hormuz is alpha software and has not received a third-party security review. Do not expose the current development server directly to the public internet.

The supported security boundary covers the AI gateway/control plane. The built-in context repository and related retrieval/lifecycle/MCP/injection components are deprecated experimental compatibility surfaces under [ADR 0008](docs/decisions/0008-gateway-product-boundary.md); ordinary provider traffic does not open their content-bearing database. Organizations should not deploy that experiment as a new production knowledge store.

The repository's versioned [threat model](docs/THREAT_MODEL.md) is validated in CI and maps known trust-boundary risks to current controls and open release gates. It is internal engineering evidence, not the independent penetration/security review required by issue #9.

## Current guarantees

- Employee bootstrap or OIDC credentials are never forwarded to OpenAI or Anthropic.
- Provider credentials are read from server-side environment variables.
- Configured OpenAI and Anthropic upstreams require HTTPS unless the hostname is a literal loopback address or `localhost` for deterministic development. Provider URLs containing user credentials, queries, or fragments fail configuration validation before a server or usage store is created.
- Provider redirects are never followed. A 3xx response becomes a fixed `502` and an unpriced, metadata-only failed-usage event; Hormuz does not send the provider credential or request to the redirect target, reflect its `Location`, or retain the target.
- Prompt and response bodies are relayed in memory and are not written to the usage database.
- Routine control-plane observability is content-free. Usage, DLP, approval, session-security, and context-read/mutation evidence retain bounded identity, scope, policy, outcome, count, token, cost, and opaque lineage metadata—not prompts, responses, matched values, raw provider queries or headers, OAuth authorization codes, filenames, source content, credentials, or internal exception text. The versioned `hormuz.content-free-schema.v2` exact-column manifest is checked at every local store startup; v2 adds only the governed model alias to short-lived budget reservations so per-model capacity can be enforced. A missing or additional routine-telemetry column fails closed with a fixed error until the manifest receives explicit privacy review. HTTP access logs use fixed route labels plus method/status/query-presence metadata and never emit the raw request target, including in verbose mode. Provider-connection failures return a fixed public error rather than the underlying exception or credential environment-variable name.
- Usage storage contains identity, team, client, protocol, model, policy outcome, token, cost, status, and bounded opaque provider-request metadata. Provider-returned model and request IDs must match gateway-owned ASCII identifier grammars before persistence; unsafe values are omitted rather than reflected or retained.
- Configurable egress controls inspect JSON string values and keys, up to three bounded strict-UTF-8 decoded views of the provider URL query, and the exact allowlisted caller-controlled provider-header values for high-confidence credential formats, every configured Hormuz/provider credential, valid hyphenated US SSNs, Luhn-valid card candidates, low-confidence email syntax, and bounded organization dictionaries before upstream serialization. Allowlisted provider-request header values must first be at most 1,024 bytes of visible ASCII plus horizontal tab; folded, control-bearing, non-ASCII, or overlong values fail before DLP, policy accounting, or provider work. The controls decode bounded UTF-8 base64/base64url strings and textual data URIs up to three layers, plus bounded printable UTF-8 revealed by percent escapes or hexadecimal text. Base64 is re-encoded only when transformed; percent/hex findings requiring transformation fail closed because rewriting those application-specific forms is ambiguous. JSON keys, raw queries, and forwarded headers are never mutated; a credential or DLP finding that would require redaction in any of them denies the complete request instead.
- Provider-format-aware DLP denies recognized OpenAI image/file/screenshot inputs and Anthropic image or non-text document/file inputs by default. It records only rule metadata and counts; it does not persist the URL, file ID, filename, encoded bytes, or surrounding content. Explicitly turning this rule off exempts only the recognized opaque objects; inspectable sibling values still pass through credential and DLP enforcement.
- DLP rules support provider and exact routed-model scopes plus detect, redact, deny, and approval-required actions. Authenticated team/person overlays may narrow scope and choose only a stronger organization action; actions equal to or weaker than the organization rule, unknown scopes, cross-organization-ambiguous team IDs, and broader provider/model scopes fail configuration validation. Optional approvals require a separate `dlp_approver`, reject self-approval, bind a keyed canonical operation/body/raw-query/forwarded-header fingerprint to event-time scope and effective policy, expire after 15 minutes, and atomically permit one retry.
- Security evidence stores only policy/rule metadata and counts, never matched values.
- OpenAI Responses requests are forced to `store: false`, and background mode is denied, unless an administrator explicitly allows those storage modes.
- Identity-token comparisons use constant-time comparison.
- OIDC JWT access tokens require a configured issuer and audience, asymmetric signature verification, expiry, a key ID, and an explicit issuer-subject mapping. Discovery and JWKS use bounded responses and HTTPS outside loopback tests; unknown key IDs cannot trigger unlimited refreshes.
- The application supplies an explicit bounded accept-backlog hint when activating its listening socket. Accepted HTTP connections then have a separate configurable ceiling acquired before a handler thread is created, and complete request headers have an absolute wall-clock deadline enforced by one bounded server-wide watchdog, including continuously trickled and subsequent keep-alive headers. Pre-parse saturation and header expiry hard-close the socket with fixed content-free diagnostics and no provider or usage work. Request bodies have configurable size and absolute-duration limits. Parsed non-health requests have a separate atomic concurrency ceiling and fail content-free before authentication or body processing when capacity is exhausted. Provider opening, body acquisition, and downstream relay share one configurable wall-clock deadline; a partial response is closed and accounted as failed when that deadline expires.
- Model aliases and upstream model IDs are bounded ASCII identifiers at configuration load, and caller model values are rejected before policy, logging, response metadata, storage, or provider work if they could inject HTTP/log control data.
- Provider response `Content-Type`, request IDs, processing-time, and rate-limit metadata pass through a gateway-owned ASCII, length, name, and duplicate boundary before downstream headers. Unsafe values are omitted with content-free diagnostic counts; response bodies continue through the ordinary provider-compatible path and are not copied into telemetry. The metadata-only usage parser caps its input buffer at 1 MiB per SSE line or 10 MiB for a non-stream JSON response, discards oversized or malformed accounting metadata without changing downstream bytes, and releases its transient buffers at completion. Only complete input/output usage from a non-stream response or terminal stream event receives an estimated cost; otherwise the content-free usage event is explicitly unpriced.
- In the deprecated context experiment, the local MCP adapter has no direct context-store or provider access. It sends only the documented narrowing fields to the authenticated Context Pack API, refuses plaintext HTTP outside loopback, does not follow redirects, bounds messages and responses, and writes only protocol messages to stdout.
- In the deprecated context experiment, governed-context authorization and freshness checks occur before lifecycle scanning or ranking. Exact server-side lifecycle snapshots invalidate mismatched `git:` source revisions and explicit dependencies; structured contradictions are excluded and surfaced rather than silently merged.
- The private-container release workflow accepts only an annotated version tag matching `pyproject.toml` on a commit reachable from `main`, separates package/signing permission from GitHub-release permission, signs the exact multi-platform digest and SLSA v1 predicate with GitHub OIDC, verifies the exact workflow identity plus decoded source/build predicate, refuses public or unlinked package state, and never publishes `latest`. Python workflows install the exact six-wheel Python 3.11+ cross-platform build closure with `--require-hashes --only-binary=:all:`, disable backend isolation, validate the lock from the selected commit, and bind its digest into metadata-only reproducibility evidence. Ordinary source/test, isolated-wheel, tag-verification, and upstream-canary environments separately install the exact multi-platform runtime closure with hashes and binary-only enforcement, install Hormuz with `--no-deps`, and require `pip check` to pass. Pinned official-client tests use exact Node/npm versions plus a validated 16-package npm lock with SHA-512 integrity and official-registry URLs; npm lifecycle scripts are disabled globally, only the reviewed Claude Code native-binary linker is invoked explicitly, and tag compatibility executes in a separate read-only job from artifact production.
- Ordinary and tag verification export the exact checked-out commit twice per platform to isolated contexts, require the active `docker-container` builder to run reviewed BuildKit `v0.32.2` from its pinned multi-platform digest, perform clean `linux/amd64` and `linux/arm64` OCI builds with a commit-derived epoch, validate all OCI descriptor digests and sizes, and require exact same-platform layout equality. Each accepted deterministic tar and `hormuz.reproducible-oci.v1` manifest contains builder, image, and source digests but no source, workspace path, prompt, response, credential, or wall-clock timestamp.
- Usage/security and governed-context audit exports can opt into canonical `hormuz.audit-chain.v1` wrappers. An independent config-free verifier requires an externally retained count and chain head, optionally binds the exact file digest, and rejects mutation, deletion, insertion, ordering, duplication, noncanonical JSON, unsafe-file, and bounded-resource failures without reflecting input content.
- Configuration loading is bounded to 1 MiB, 64 nesting levels, and 100,000 decoded nodes of UTF-8 JSON; it rejects duplicate object members and non-standard numeric constants at every depth and computes the exact-file SHA-256 before secret resolution or side effects. An optional separately supplied expected digest stops startup on any byte change without reflecting configuration content.

## Current limitations

- The built-in server does not terminate TLS.
- The reference container is pinned, non-root, restricted by its documented run command, smoke-tested, SBOM-producing, gated on high/critical vulnerability findings, and subject to exact-source two-build OCI byte-equality gates for `linux/amd64` and `linux/arm64` in CI. The comparison builds disable provenance and SBOM attestations because those envelopes are run-specific; the separately signed release build still produces and verifies them. The equality claim does not cover every BuildKit implementation or host, offline base/dependency availability, or a published registry digest. Those controls do not make the single-node SQLite topology highly available.
- The repository does not yet protect `v*` tags with a ruleset or require a protected release-environment reviewer. Repository administrators can change workflows and refs; tag authority, emergency revocation, package retention, customer-registry copies, and KMS/offline signing remain open governance decisions.
- The audit chain is generated from the selected export, not when each database event is committed. It is neither a signature nor a durable global sequence: it cannot expose a record deleted before export, authenticate an anchor stored beside the file, unify separate stores/exports, or replace KMS custody, an immutable external sink, retention/legal-hold policy, or restore drills.
- Public-good Sigstore keyless signing may disclose workflow identity, tag, digest, certificate, and timestamp metadata through public transparency infrastructure even while the source repository and image remain private. The release workflow fails closed unless the owner-controlled `HORMUZ_SIGSTORE_RELEASE_APPROVAL` repository variable records acceptance of that bounded disclosure.
- Static environment-provided identity tokens remain available for bootstrap and break-glass use.
- The workload OIDC path verifies short-lived JWT access tokens. The human path implements authorization-code + PKCE browser login and issues opaque, rotating Hormuz credentials from a separate local session store.
- Raw Hormuz access/refresh credentials are not stored server-side. The session database uses keyed hashes, encrypts transient PKCE state, rotates both credentials, and revokes a family on refresh replay.
- The CLI permits persistent human login only through allowlisted macOS Keychain, Windows Credential Manager, or Linux Secret Service/KWallet backends. Plaintext keyrings fail closed.
- Provider access/refresh tokens are not retained after the OIDC callback. ID tokens are never accepted as gateway bearer credentials.
- Real-IdP validation, SCIM provisioning/deprovisioning, administrator revocation APIs, distributed throttling, KMS-backed custody, and HA session persistence remain release gates.
- SQLite is a single-node development store.
- Configuration contains rate cards and policy. Hormuz rejects duplicate or unknown fields throughout its owned configuration objects without reflecting rejected keys, validates model and policy-scope references, can require an exact artifact digest, and treats one accepted snapshot as immutable for the process lifetime. The digest is not a signature; there is still no signer identity, approval authority, live reload, deployment-coordinated rollback, or change-approval workflow.
- Structured DLP remains deterministic and does not understand image/file contents. Recognized provider media blocks are denied rather than decoded. Supported encoded text is limited to single-string standard or URL-safe base64, textual data URIs and ASCII MIME whitespace, percent escapes, and hexadecimal text that decode to bounded, predominantly printable UTF-8. Recognized encoded compression/archive signatures are denied as opaque media by default rather than decompressed. Unknown or obfuscated encodings, non-ASCII whitespace, archive contents, unrecognized binary payloads, application-specific repeated URL-query decoding, source paths, and semantically sensitive company information remain unclassified. Non-UTF-8 percent/hex text is unsupported, while non-UTF-8 percent-encoded provider queries fail closed. Email matching remains detect-only; organization evaluation, approval notifications/queue UX, production HA proof, and KMS-backed approval-key custody are open gates.
- The deprecated context experiment quarantines narrow high-confidence policy-override, secret-exfiltration, or instruction-escalation patterns before ranking. This is not comprehensive semantic prompt-injection detection and is not a supported gateway guarantee.
- Content-free control-plane observability does not mean Hormuz never handles content. The gateway must inspect provider-bound plaintext transiently to enforce policy and relay it. Explicit use of the deprecated context experiment also opens a separately configured content-bearing repository; that store is outside the supported Hormuz product boundary and requires its own encryption, authorization, retention, deletion, and audit controls.
- MCP makes returned context available to the model but does not itself enforce tool use or prevent an unrecognized injection. Provider-bound tool results are inspected by the existing egress controls when the client sends the next model request through Hormuz.
- Lifecycle snapshots are trusted operator/connector input. The local snapshot store contains artifact URIs and revisions, while metadata-only lifecycle audit events contain only scope, versions, hash, and artifact count.
- Log shippers, reverse proxies, load balancers, crash reporters, service meshes, and provider behavior remain deployment-specific boundaries. They must be configured not to capture raw URLs, bodies, headers, or process dumps; Hormuz's application-level guarantee cannot sanitize an upstream component that records traffic before Hormuz receives it.
- The built-in backlog hint, connection ceiling, and absolute header/body bounds are process-wide, not per-source or distributed controls. Health probes also require a connection slot. The operating system may cap or reinterpret the requested backlog, and its SYN queue and network-wide limits remain platform-managed. A shared deployment still requires a hardened reverse proxy or WAF for TLS, source-aware limits, an independently configured slow-body defense, and coordinated replica capacity.

Terminate TLS and enforce network access controls in front of Hormuz for any shared test deployment. Use unique identities for every human or service account, never shared team credentials. Do not send an OIDC ID token where an API access token is required.

Report security issues privately to the repository maintainers. Do not include real API keys, identity tokens, prompts, responses, or customer data in a report.
