# ADR 0005: Generic key custody with optional AWS and self-hosted Object Lock profiles

- Status: **Accepted**
- Decision date: 2026-08-21
- Decision owner: Product owner
- Approval record: [issue #17 design decision](https://github.com/Xpounder-com/hormuz/issues/17#issuecomment-5377270265)
- Implementation issue: [#17](https://github.com/Xpounder-com/hormuz/issues/17)

## Decision

Hormuz will expose provider-neutral envelope-key and immutable-audit-anchor
contracts. AWS KMS and S3 Object Lock remain an optional reference
implementation and certification target. An account-free profile uses OpenBao
Transit plus a customer-operated S3-compatible Object Lock service. Both
integrations are optional at package install time and must be enabled
explicitly in deployment configuration.

1. A `DataKeyProvider` generates, decrypts, and re-wraps encrypted data keys.
   A separate `AuditAnchorSink` receives complete, verified audit artifacts.
   Neither interface exposes a provider master key or assumes AWS elsewhere in
   Hormuz policy, identity, or routing code.
2. `key_custody` names customer-managed key references by purpose:
   `provider_credential`, `identity_connector_secret`, `session_material`,
   `approval_fingerprint`, and `data_encryption`. A configured AWS profile
   rejects duplicated references across purposes. An AWS profile uses ambient
   workload credentials; an OpenBao profile uses a named process-environment
   token. Neither accepts a static credential in JSON configuration.
3. An encrypted envelope is a strict versioned AES-256-GCM object. Its data
   key is generated by the provider and authenticated with a deterministic
   tenant fingerprint and purpose. The envelope contains ciphertext, nonce, and encrypted data key
   only. The owner-only `custody seal` command accepts a source environment
   variable and never prints its value; `custody rewrap` calls provider-side
   re-encryption rather than exposing a secret or plaintext data key to an
   administrator.
4. A provider credential may be configured through an encrypted envelope file
   instead of `api_key_env`. The gateway resolves that file during startup,
   checks owner-only permissions, decrypts it in process memory, and makes it a
   protected redaction value. It fails closed rather than falling back to an
   environment source.
5. `audit-anchor` is an explicit operator command. It accepts only current,
   metadata-only tenant audit events, creates a versioned SHA-256 hash chain,
   verifies it, and writes one S3 object under Object Lock `COMPLIANCE` mode
   with optional legal hold. The AWS profile uses SSE-KMS; the self-hosted
   profile envelope-encrypts the entire artifact before S3 egress. Raw tenant
   identifiers are hashed in the object-key path.

## Consequences

This is the first usable KMS/BYOK and immutable-retention slice. It keeps the
core wheel free of an unconditional cloud or S3 SDK dependency. A self-hosted
deployment installs `hormuz[self-hosted]`, supplies an OpenBao token and
dedicated S3-compatible storage credentials through named process-environment
variables, configures purpose-separated Transit keys, and creates an
Object-Lock-enabled bucket before using the commands. An AWS deployment
continues to install `hormuz[aws]` and uses normal AWS workload identity.

The audit artifact detects alteration, deletion, insertion/reordering,
duplication, and cross-tenant rows **after the artifact is created**. S3 Object
Lock protects that artifact and its chain head from replacement during the
configured retention period. It does not prove that a mutable source database
did not lose a row before the next explicit anchor; commit-time database
chaining and automated delivery are separate work.

Customer-managed AWS KMS keys provide the intended BYOK deployment boundary:
the customer owns KMS policy, rotation, disablement, and deletion protection.
Imported KMS material, CloudHSM, and external key stores may be used by a
customer only after their exact operational profile is separately verified.

The generic self-hosted adapter is deliberately not a storage-provider
certification. Every candidate must pass an opt-in, real-service conformance
run that proves data-key operations, encrypted artifact recovery, versioning,
Object Lock `COMPLIANCE` retention, legal hold, and failure behavior. A
single-node local composition, once added, proves integration only; it does
not protect against a host or storage administrator and is not a production
immutability claim.

## Rejected alternatives

- **Static keys or secret values in Hormuz configuration:** rejected because
  configuration is not an enterprise secret store.
- **Custom cryptography or locally generated wrapping keys:** rejected because
  a production custody boundary needs managed-key authorization, auditing, and
  rotation semantics.
- **S3 versioning without Object Lock:** rejected because a versioned object is
  still mutable/deletable by a sufficiently privileged bucket principal.
- **Retaining unencrypted audit artifacts in a self-hosted store:** rejected
  because a storage read capability should not expose metadata-only employee or
  audit content. The account-free profile encrypts the complete artifact before
  object-store egress.
- **Naming a storage product as certified before live WORM evidence:** rejected
  because S3 API compatibility alone does not prove compliance-mode retention
  is actually enforced.
- **An AWS-specific core policy model:** rejected because cloud choice belongs
  at a provider adapter boundary, not in gateway policy semantics.
