# ADR 0010: v1.1 portfolio intelligence and use-case economics contract

- **Status:** Accepted
- **Decision date:** August 29, 2026
- **Decision record:** [issue #212 comment](https://github.com/Xpounder-com/hormuz/issues/212#issuecomment-5466284033)
- **Implementation gate:** [issue #212](https://github.com/Xpounder-com/hormuz/issues/212)
- **Release epic:** [issue #226](https://github.com/Xpounder-com/hormuz/issues/226)
- **Machine-readable contract:** [portfolio-intelligence-contract-v1.json](../portfolio-intelligence-contract-v1.json)
- **Field-level wire schemas:** [portfolio-intelligence-wire-v1.json](../portfolio-intelligence-wire-v1.json)

## Context

Hormuz v1.0.0 governs requests that pass through the gateway. It authenticates
an employee or workload, pins policy, reserves applicable budgets, routes or
denies the request, protects provider-bound data, and retains metadata-only
request, usage, cost, security, and audit evidence. That foundation answers
which governed traffic occurred and what policy and estimated cost applied.

Organizations also need to decide where AI budget should go and which model is
fit for a particular kind of work. Token volume or spend alone cannot answer
that question. A lower-cost model may increase retries, review work, latency,
or defects; a higher-cost model may be economical for one use case and wasteful
for another. Conversely, a ticket or pull request moving after an AI request is
only an observed association unless a controlled design supports a causal
claim.

The next release therefore needs a portfolio-intelligence plane without
weakening the enforcement gateway, rewriting the v1 ledger, ingesting work
content, or turning operational analytics into employee surveillance. It also
needs an explicit compatibility boundary: the target is a backward-compatible
minor release, not a silent rewrite of v1 request, response, authentication,
error, or durable-evidence semantics.

## Decision

### Release and product boundary

The capability ships under the target version **v1.1.0**. It is an additive
minor release over immutable v1.0.0. Hormuz remains the enforcement gateway and
source of governed request, policy, token, cost, and audit facts.

Portfolio intelligence is a separate append-only plane:

```text
organization policy and budget plan
                |
                v
governed request attempt ──> immutable v1 usage/cost/audit evidence
                |
                +──> append-only use-case attribution
                              |
external work observations ──+──> evidence-qualified association
                                      |
                                      v
                         per-use-case model scorecard
                                      |
                                      v
                         reviewable policy recommendation
```

The v1 usage event is not extended in place and historical rows are not
backfilled with guessed work context. New durable objects link through stable
opaque identifiers. #213 creates the composition seam; the feature repositories
remain distinct from the v1 usage-ledger repository even when they share a
database and transaction.

### Work-scope hierarchy

The canonical hierarchy is:

```text
organization
└── portfolio
    └── initiative
        └── use_case
```

An organization may omit intermediate grouping levels. Every work scope has
one parent to the nearest configured ancestor; cycles and cross-organization
parents are forbidden. A `use_case` is the primary analytic and model-selection
unit. Portfolio and initiative views aggregate descendant use cases while
retaining each descendant's coverage and guardrails.

Opaque IDs are stable and never reassigned. Material changes to hierarchy,
ownership, binding, or analytic meaning append a new immutable version. Active,
archived, and tombstoned states do not erase linked financial or audit facts.
An administrator may provide one bounded display name for an authorized view,
but external ticket/project titles and descriptions are never copied into the
registry, routine evidence, logs, or exports.

Canonical identities and lifecycle ownership are:

| Object | Canonical identity | Lifecycle |
| --- | --- | --- |
| Organization | Existing server-resolved `organization_id` | Owned by the existing tenant/identity boundary; the portfolio plane cannot create or mutate it. |
| Work-scope version | `organization_id`, `work_scope_id`, `version` | `active`, `archived`, `tombstoned` |
| External work object/binding | `organization_id`, `connector_id`, `external_object_id`; each change has a binding-event ID | `active`, `superseded`, `tombstoned` |
| Governed run | `organization_id`, immutable v1 `request_attempt_id` | Existing `pending`, `succeeded`, `failed`, `rate_limited`, `outcome_unknown` states |
| Attribution | `organization_id`, `attribution_event_id` | `active`, `superseded`, `voided` |
| Outcome | `organization_id`, `connector_id`, `source_event_id` | `observed`, `superseded`, `tombstoned` |
| Association | `organization_id`, `association_event_id` | `unmatched`, `ambiguous`, `associated`, `excluded`, `superseded` |
| Budget plan | `organization_id`, `budget_plan_id`, `version` | `active`, `superseded`, `expired`, `tombstoned` |
| Scorecard | `organization_id`, `scorecard_id`, `version` | `eligible`, `inconclusive`, `expired`, `superseded` |
| Recommendation | `organization_id`, `recommendation_id`, `version` | `pending`, `accepted`, `rejected`, `expired`, `invalidated`, `superseded` |

IDs are opaque, stable, tenant-qualified, and never reassigned. A reference
across organizations is invalid even if the opaque component happens to match.

### Time, correction, idempotency, and retention

Every normalized event keeps event time, observation time, and ingestion time
separate. Event time is the source or domain occurrence time as observed;
observation time is when the connector observed it; ingestion time is the
database commit time and is authoritative for receipt and retention. A
source-supplied time never authorizes scope or overrides ingestion time.

Current state is derived deterministically from an entity version or source
revision, then ingestion time and opaque event ID. Late events are retained and
may produce a new derived snapshot; they never rewrite earlier events. A
correction appends an event naming the prior identity, authorized actor, and
fixed reason code. The same idempotency identity plus the same canonical
request returns the same result; conflicting content for one identity fails
closed.

Deletion is a tombstone event, not erasure of linked financial or audit facts.
The customer-controlled self-hosted retention boundary remains authoritative,
including for backups and exports, and Hormuz makes no universal-erasure
claim.

### Governed-run attribution

One request attempt has at most one active primary use-case attribution. This
rule prevents spend and outcomes from being counted as primary work for
multiple use cases. Missing, invalid, ambiguous, stale, or unsupported
attribution remains visible; Hormuz never infers it from prompt text, model
output, filenames, source code, ticket content, or employee behavior.

The accepted sources are:

1. optional authenticated request metadata in `X-Hormuz-Work-Scope`;
2. a server-side default binding already authorized for the identity/client;
3. a separately authorized post-run binding to an immutable request-attempt ID.

At request time, explicit authorized metadata takes precedence over a
server-side default; otherwise the attempt is unattributed. A later authorized
post-run binding may append or supersede the current attribution. The fixed
confidence classes are `explicit_authorized`, `server_side_default`,
`authorized_post_run`, `unattributed`, and `ambiguous`. They describe binding
source quality, not causal or statistical probability.

Coverage always exposes eligible governed attempts, eligible governed spend,
eligible external outcome events, and eligible association candidates.
Unattributed, ambiguous, unmatched, excluded, late, and unsupported members
stay in their applicable denominator.

Request metadata is resolved only after authentication, is checked against the
server-known organization and work registry, and is stripped before provider
egress. Invalid or unauthorized explicit metadata fails before budget
reservation and provider egress. Absence is recorded as unattributed unless an
active policy requires attribution, in which case it fails closed. Post-run
corrections append a superseding event with an actor, reason code, and event
time; they do not mutate request, usage, cost, policy, or earlier attribution
evidence.

### Budget combination

Work-scope budgets supplement rather than replace current controls. Every
applicable organization, team, actor, application/client, portfolio,
initiative, and use-case rule is evaluated. Denies win, allowed model sets may
only narrow through intersection, and the lowest applicable numeric ceiling
wins.

A governed request reserves the conservative request-time amount atomically
before provider egress. The reservation is bound to the event-time work-scope
and budget-plan versions. Success, failure, rate limit, and ambiguous outcome
retain the existing no-automatic-replay and uncertain-reservation rules.

Provider-final cost, provider aggregate, configured-rate-card estimate,
allocated estimate, credit/discount, and unavailable cost are different bases.
No aggregation or report may relabel one basis as another. In particular, a
provider aggregate cannot become a final per-request, team, use-case, or
employee invoice fact.

### Work observations and evidence quality

GitHub and Linear connectors normalize an exact allowlist of lifecycle and
quality observations into `hormuz.work-outcome-event` v1. Connector tenant
scope comes from an authenticated server-side installation/workspace binding,
not a payload field. Signatures are verified over exact raw bytes before JSON
parsing. Raw payloads and work content are not retained.

Evidence levels are fixed:

- **descriptive:** a source observation without a governed-run association;
- **associated:** a deterministic, auditable observational link between a run
  and a work observation; and
- **controlled:** a result from a separately approved, predeclared controlled
  design with its own eligibility and guardrails.

Connectors produce descriptive evidence. Deterministic joins produce associated
evidence. v1.1.0 never upgrades evidence to controlled automatically. Temporal
proximity, a shared actor, or a shared use case is not by itself causality.
Unmatched, ambiguous, excluded, late, superseded, and unsupported evidence
stays in coverage denominators instead of disappearing.

Every decisive metric uses a versioned, predeclared per-use-case eligibility
rule and explicit minimum coverage and sample thresholds. There is no universal
numeric threshold: the accountable owner must version the thresholds for the
use case before the window opens. Missing thresholds or evidence below either
threshold produces `inconclusive`, never a winner.

### KPI and model-comparison contract

The three primary decision metrics are:

1. **Use-case-attributed spend coverage:** eligible governed spend with valid
   use-case attribution divided by eligible governed spend, with pricing,
   connector, association, and exclusion coverage shown separately.
2. **Quality-qualified cost per accepted work item:** all eligible attempts,
   retries, failures, and supported cost components divided by source-qualified
   accepted work items. If no eligible item is accepted, the metric is
   undefined/inconclusive rather than zero.
3. **Optimization lift versus a declared baseline:** the qualified economics
   difference between comparable model/policy cohorts. Observational output is
   labeled associated; `verified` lift is reserved for controlled evidence.

Drivers may include actual-model mix, token/cache mix, latency, retries,
first-pass success, fallback, denial, and provider failure/rate-limit rates.
Quality, reversion/defect, reliability, privacy, budget, coverage, sample,
freshness, and comparability are mandatory guardrails.

Scorecards are keyed by organization, work-scope version, time window, actual
provider/model version, policy version, rate-card version, cost basis,
connector coverage, and association-rule version. Requested, routed, and
provider-reported actual models remain distinct. A scorecard publishes the
Pareto-efficient set across cost, quality, latency, and reliability for one use
case. Hormuz does not publish a universal model rank. A composite can exist
only with explicit versioned owner weights and sensitivity that exposes losing
tradeoffs. Insufficient evidence produces `inconclusive`.

### Authorization and employee boundary

The existing static-token or OIDC bearer authentication boundary remains. New
portfolio capabilities add separate tenant-qualified authorities:

- `portfolio_admin` mutates authorized organization registry/budget objects;
- `finance_viewer` reads authorized financial aggregates and coverage;
- `platform_viewer` reads authorized operational/model aggregates; and
- `team_lead` reads one authorized team and descendant work scopes.

The existing self scope remains limited to the authenticated actor's own usage
view. It cannot join portfolio outcomes, peer records, or employee comparisons.

Roles are resolved server-side before query planning or storage access. A body,
filter, cursor, webhook, or connector payload cannot widen identity-derived
scope. Privileged reads are audited before results are delivered. None of
these roles grants model-provider access, inference entitlement, policy root
authority, or another tenant's data.

Portfolio APIs do not rank, score, or compare employees. Person-level usage
retains its existing self/authorized operational boundary and cannot be joined
into an employee performance score.

### API and compatibility boundary

New administrator resources live under `/v1/admin/portfolio`; connector ingress
lives under `/v1/connectors`. The exact route inventory is frozen in the
machine-readable contract. Its 21 route bindings name every Hormuz-owned
request and response schema at version 1, including work bindings, budget-plan
activation, and recommendation decisions. GitHub and Linear webhook request
bodies remain provider-owned signed bytes; only the normalized event and
content-free receipt are Hormuz-owned schemas. Collection endpoints use opaque frozen-window
cursors, a default page size of 50, a maximum of 100, deterministic
time-plus-ID ordering, and cursors bound to tenant, role, filters, window,
ordering, and schema. Mutation endpoints require an idempotency key. Connector
ingress uses verified source-delivery identity instead.

The linked wire bundle concretely defines all 26 Hormuz-owned payloads: one
typed query, seven JSON mutation requests, eight entity/evidence records,
eight collection pages, and receipt/error envelopes. Every object is closed;
fields have explicit requiredness, nullability, bounds, enums, and semantics.
The bundle is digest-pinned by the contract gate, and the same digest covers
its transport and domain rules. It is a planned contract, not registration or
activation of runtime schemas or handlers.

Budget-plan creation stores an immutable version without applying it. A null
activation lifecycle denotes a never-activated version; the separate active
pointer and generation are changed only by explicit authorized activation.
Recommendation acceptance records a reviewed decision and cannot itself apply
policy. These representations preserve the existing no-automatic-application
decision rather than introducing new authority.

Reads may be retried safely. A mutation or connector delivery may replay only
through its verified idempotency identity; a timeout never authorizes replay of
provider work.

Requests reject unknown fields and validate before domain work. Responses are
explicitly shaped contracts and never expose database rows. New administrator
errors use `hormuz.portfolio-error` v1. Provider-compatible routes preserve the
provider-native body and convey a new work-scope classification only through a
versioned Hormuz header contract.

The existing v1 routes, required request fields, response fields, authentication
rules, error codes, status behavior, pagination, ordering, retry semantics, and
schema entries remain unchanged. New routes and new schema identities are
additive. Any required-field addition, removal, rename, type/semantic change,
auth change, error change, or behavior change requires a compatibility adapter
or a future major release.

Breaking v1 changes require a compatibility adapter or a future major release.

The immutable v1.0.0 contract-manifest fixture intentionally preserves its
historical `current_release_line: 0.2` value. Current `main` is byte-equivalent
to that fixture. Correcting the label by silently changing the v1 manifest is
forbidden; #214 must version the corrected manifest or document a compatible
adapter as part of the exact v1.0.0→v1.1.0 transition.

### Recommendation boundary

A recommendation is an immutable, expiring decision-support record bound to
one work-scope version, active policy digest, scorecard snapshot, evidence
level, data window, coverage, guardrails, rate cards, and actual model versions.
Allowed changes are limited to budget plans, model allowlists/fallbacks,
output/cost caps, and routing policy.

Before an administrator may accept a recommendation, Hormuz performs semantic
compare, request preview, saved-scenario evaluation, and rollback planning.
Policy or scorecard drift invalidates the recommendation. Acceptance still uses
the existing authorized policy activation path. Hormuz never automatically changes
a model, route, cap, budget, or policy.

### Content and retention boundary

Durable portfolio state may contain opaque tenant, actor, team, application,
work, provider, model, policy, rate-card, and connector identifiers; bounded
administrator-supplied work-scope display names; timestamps; counts; durations;
tokens; exact cost components; fixed lifecycle/quality/coverage/reason codes;
keyed digests; and content-free provenance.

It excludes prompts, responses, patches, source content, filenames/paths,
ticket/project/initiative titles or bodies, comments/review text, external
repository/workspace/branch names, labels containing free text, attachments,
raw connector payloads, matched detector values, credentials, and secret
values. Debug content is outside this contract and disabled by default. Release
and pilot evidence is content-free.

Append-only financial and evidence records use supersession and tombstone
events. Tombstoning a registry label does not delete linked facts. The customer
operating the self-hosted database retains backup, export, retention, restore,
and deletion authority under the existing durable-data boundary; Hormuz makes
no universal erasure claim.

## Consequences

- #213 may refactor the storage composition boundary without feature behavior.
- #214 first accepts per-feature compatibility plans and red-first transition
  tests after the feature-free #213 seam. Feature PRs must pass those tests;
  #214 stays open for exact final-candidate binary, schema, API, migration,
  rollback, and recovery proof before the v1.1.0 tag.
- #215 through #224 have one accepted entity, security, evidence, KPI, API, and
  recommendation contract to implement.
- #8 remains a release gate because a model-economics scorecard cannot present
  unqualified estimates as finance facts.
- #225 can pre-register an external pilot without inventing causal or
  production-readiness claims.
- A future content-bearing connector, browser-session requirement, HA/SLA
  claim, independent certification claim, or broad multi-profile transition
  activates the conditional issues named in the machine-readable contract.
- Changing the hierarchy, single-primary-attribution rule, cost-basis meaning,
  evidence levels, authorization boundary, KPI definitions, automatic-policy
  prohibition, content boundary, or compatibility rule requires a superseding
  ADR and a new contract version.

## Nonclaims

This decision does not implement a repository, migration, connector, endpoint,
scorecard, recommendation engine, or pilot. It does not prove final invoice
accuracy, broad customer value, universal ROI, causal productivity improvement,
employee performance, content governance, HA/SLA readiness, or independent
security certification.
