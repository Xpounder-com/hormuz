# Codex cloud authorization without paid API fallback

Date checked: 2026-10-15. Research for [Determine the documented Codex cloud authorization path without paid API fallback](https://github.com/Xpounder-com/hormuz/issues/539), within [Finish the customer-local router within the approved architecture](https://github.com/Xpounder-com/hormuz/issues/536).

This is a capability finding and qualification plan, not an authorization grant or a successful product qualification. No sign-in, app registration, credential-cache access, provider request, model acquisition, client configuration change or runtime test was performed.

## Conclusion

OpenAI documents **two distinct ways to use a ChatGPT plan without supplying a Platform API key**:

1. Native Codex can forward its own ChatGPT-authenticated model-provider requests through a gateway. The documented deployment uses a supported client and workspace-managed provider requirements, with gateway authentication kept separate from the ChatGPT credential. [Native gateway setup](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway)
2. An eligible open-source or locally hosted app can obtain its **own** user-authorized registration and OAuth grant for eligible public Responses API calls. Eligible Plus and Pro users can authorize plan usage; identity sign-in alone is insufficient. [Integration availability and scopes](https://developers.openai.com/siwc/quickstart), [open-source/local-app scope](https://developers.openai.com/siwc/token-sharing-open-source)

Hormuz does not yet implement or qualify either path. Existing generic API-key transport is not evidence of plan eligibility. For the approved existing-client architecture, native forwarding is the first path to assess; the documented managed-workspace deployment does **not** establish a zero-tweak personal-account/plugin installation. If that deployment cannot serve the selected first-release users, the owner must choose a supported app-specific authorization integration or defer cloud support. Do not recover either path by borrowing native credential files or silently enabling paid API billing. [Approved scope](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/docs/ROUTER_SCOPE.md), [current transport](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/server.py#L1754-L1830)

## Paths and credential ownership

| Path | Authorization owner and destination | Required evidence before support |
| --- | --- | --- |
| Native Codex through Hormuz | Codex obtains and refreshes its native ChatGPT credential; Hormuz separately authenticates the caller, consumes its gateway credential and forwards the ChatGPT headers only to the Codex backend. | Supported client/build, permitted workspace and managed configuration, separate gateway auth, correct native model catalog and completed conversation. |
| Hormuz-specific ChatGPT-plan authorization | Hormuz obtains an issued client registration and scoped OAuth tokens with user consent; its cloud destination calls the public Responses API. | Eligible app/user/workspace, validated identity and granted plan scope, protected token lifecycle, supported request shape/model and completed inference. |
| Ordinary identity or connector sign-in | The identity/connector flow establishes its own identity or service permission. | It supplies no plan entitlement by itself; do not convert an ID token or connector credential into a model credential. |
| Platform API key | The configured API organization/project supplies a provider credential and pays API rates. | A separately chosen, explicitly authorized billing path. It is not a fallback for denied or exhausted plan usage. |

The table summarizes [native gateway ownership](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway), [identity versus inference permission](https://developers.openai.com/siwc/quickstart), and [Codex sign-in/billing distinctions](https://learn.chatgpt.com/docs/auth).

### Native Codex forwarding

The documented provider sets `requires_openai_auth = true`. Its gateway base proxies `/models` and `/responses` to `https://chatgpt.com/backend-api/codex`. Codex supplies `Authorization: Bearer <ChatGPT token>` and, when available, `ChatGPT-Account-ID`; the gateway preserves those headers for that backend. [Native gateway setup](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway)

Gateway authentication is separate. Option A obtains the gateway token before launch and delivers it through `X-Gateway-Key`; the gateway validates and removes it. The helper runs once per launch, and desktop launch integration must supply its environment. Option B requires the gateway's OAuth authorization server, a registered public PKCE client and a reachable loopback callback; native Codex manages gateway sign-in/renewal. Neither option combines the existing command-backed provider `auth` block with `requires_openai_auth = true`. [Credential delivery options](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway#how-to-set-it-up)

`requires_openai_auth = true` does not itself prove subscription billing: native OpenAI authentication supports both ChatGPT and API-key sign-in. Verify the active method and, for a supported managed deployment, require `forced_login_method = "chatgpt"` before enabling this plan-only route. [Authentication methods and restrictions](https://learn.chatgpt.com/docs/auth#enforce-a-login-method-or-workspace)

The page prescribes cloud-managed workspace requirements and a build supporting those fields. It provides no minimum version or proof for Hormuz's pinned build, and no general personal-account installation guarantee. Model traffic routing also leaves sign-in, MCP, plugins and other app paths separate. [Limitations](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway#caveats-and-limitations)

### App-specific ChatGPT-plan permission

For the documented OSS/local flow, persist a stable opaque `ext_agent_host_id` before first sign-in. Initial browser authorization uses `client_id=dynamic_agent_client` and the app's consistent `agent_name_hint`; OpenAI issues a user/workspace-bound client ID, reused thereafter. No client secret or partner API key is required. Use fresh state, nonce and PKCE S256, an exact `127.0.0.1` loopback callback, and resource `https://api.openai.com/v1`. [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)

Request `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`. Validate callback state, then exchange the code with the issued client ID and PKCE verifier. Verify the ID token's signature, issuer, audience, expiration and nonce; require the token response's granted `chatgpt.tokens.use.direct` scope before inference. A valid login without it keeps plan use disabled. [Registration checks](https://developers.openai.com/siwc/token-sharing-open-source/sign-in#4-validate-the-id-token-and-chatgpt-plan-permission)

Keep registrations, validated identities and token sets separate across accounts/workspaces. Protect and atomically replace credentials, serialize rotating refreshes, and support logout/revocation. Do not combine a client ID with another registration's tokens. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)

Discover the selected account's model catalog with its access token, then call `POST https://api.openai.com/v1/responses` with that token. **Do not send this grant to ChatGPT `backend-api` endpoints.** Require `store: false`, `stream: true` and terminal `response.completed`; a catalog or HTTP success alone is insufficient. [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)

The preview uses replayed `input` arrays and omits HTTP `previous_response_id`. It rejects fields including `max_output_tokens`, `temperature`, `background`, `metadata` and `conversation`, and restricts tool layouts/capabilities. HTTP/SSE and supported client-side function/custom tools are distinct from unsupported hosted tools or Responses `tool_search`. A future adapter needs an explicit field/capability contract; silently dropping policy controls is unsafe. [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

OpenAI's app-server example passes the app's own access token to a child Responses provider, disables WebSockets and leaves token renewal to the app. Its bundled `model/list` catalog is not entitlement evidence. This is an embedding example, not proof that installing a skills-only plugin converts an existing desktop session to this grant; adopting an independent Hormuz agent loop would conflict with the approved architecture. [App-server contract](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server), [architecture boundary](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/docs/ROUTER_SCOPE.md)

Plan usage remains subject to user/workspace/policy and usage limits. Errors such as `subscription_sharing_user_not_eligible`, `subscription_sharing_usage_limit_exceeded` or unavailable usage checks stop or defer inference; they do not authorize changing billing. Users can manage app access and usage in ChatGPT settings. App-specific plan limits and optional ChatGPT credits are separate from Platform API-key billing; absence of an API key is not an unlimited-free-usage promise. [Recovery rules](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery), [usage controls](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#tracking-usage)

## Hormuz implementation gaps

Repository inspection used main `fb5084cb235fd9e9e82f501ce5af03c956432bf5` and, for the unmerged local-credential/shadow stack only, `75f089a7065f1e4cdc9a0b6309f6733af81cdac3`. No feature commit was merged into this research branch.

- **Destination auth is currently `api_key` or `none`.** Cloud destinations require a configured environment/envelope credential. There is no explicit native-forwarded or app-plan grant type/lifecycle. Reusing the `api_key` name for an OAuth bearer would not supply consent validation, renewal, revocation or endpoint restrictions. [Parser](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/_config_routing.py#L40-L105)
- **Native headers cannot currently pass through as required.** Ingress authenticates a Hormuz bearer/API key; upstream headers are rebuilt using the destination credential and do not preserve `ChatGPT-Account-ID`. A new adapter must authenticate the local gateway without interpreting the native ChatGPT token as its own identity token. [Ingress and forwarding](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/server.py#L1754-L1830)
- **Model discovery and paths differ.** Hormuz emits generic `/v1/models` data rather than Codex's required `models` array, exposes only its listed `/v1/*` model routes, and joins upstream paths mechanically. Setting a backend URL alone cannot establish native Codex backend compatibility. [Model catalog](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/server.py#L572-L585), [routes](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/server.py#L642-L664), [URL composition](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/server.py#L1803-L1810)
- **Shared setup currently selects local-router auth.** Main emits `requires_openai_auth = false` with `env_key`; the unmerged stack adds a local generation-bound command helper. Neither implements plan authorization. The lifetime module refuses detected managed configurations, while the documented native workspace setup requires managed delivery. Its CLI pin is `0.147.0`, not desktop qualification. [Main provider and managed guard](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/connected_client.py), [unmerged helper](https://github.com/Xpounder-com/hormuz/blob/75f089a7065f1e4cdc9a0b6309f6733af81cdac3/hormuz/connected_client.py), [qualification boundary](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/docs/CONNECTED_CLIENT_LIFETIME.md)
- **Public plan request shaping needs separate work.** Policy can insert `max_output_tokens`, which the direct-plan preview rejects. A supported adapter must preserve enforceable policy, tool semantics and continuation instead of merely forwarding a renamed bearer. [Current cap insertion](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/hormuz/server.py#L888-L902), [direct-plan limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

## Credential and privacy invariants for the eventual spec

These are derived requirements from the documented path separation and Hormuz's approved destination/admission ownership, not a new claim of implementation:

- Treat native Codex credentials, app-specific plan credentials, Platform API keys and Hormuz gateway tokens as different capabilities. Bind credential kind, allowed origin/path, account/workspace, model and generation together; deny mismatches and cross-origin redirects.
- Local inference, the shadow classifier, readiness helpers, unrelated providers and diagnostics never receive ChatGPT authorization/account headers, app tokens, gateway credentials or refresh tokens. Cloud permission cannot widen hard local-only admission.
- Forward only the native headers required by the chosen native backend; consume gateway auth locally. For app-specific grants, send access tokens only to their documented resource and refresh/revoke material only to their documented authorization service. Retained ID-token hints belong only in that service's authorization flow.
- A missing/expired/revoked grant, denied consent, unavailable model or usage limit cannot select an API key automatically. Model advice and model catalogs are observations, not authorization. Preserve conversation affinity and invalidate it when its authorized destination generation changes.

Sources: [native credential isolation](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway#keep-the-credentials-on-their-own-paths), [app credential security](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#credential-security), [execution destination ownership](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/docs/decisions/0015-execution-destination-ownership.md), [local admission](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/docs/decisions/0016-local-route-admission.md)

## Concrete qualification checklist and blocking gates

1. **Owner selects the first supported deployment.** Choose native managed-workspace forwarding, or an app-specific OSS/local grant integrated without a new agent loop. Establish whether the actual intended account/workspace and installation surface support it. The current documentation does not settle personal-plugin/native-gateway availability for this owner.
2. **Pin the client and capabilities.** Record exact CLI version/hash or desktop version plus bundled engine, Hormuz commit, provider/catalog schema, transport and chosen model. Verify every selected auth/managed field on that build. Do not reuse local-only qualification as cloud evidence.
3. **Approve the native flow and account.** Later, with explicit owner consent, use the selected native browser flow. For the gateway path verify workspace/admin authorization and gateway credential delivery. For app authorization verify issued registration, account/workspace, identity, plan scope and protected storage/refresh. No cache scraping or unrelated token import.
4. **Implement synthetic negative and positive workflows first.** Use the approved connect → request → inspect result/status → disconnect seam. Cover wrong credential kind/origin, omitted or mixed account, denied grant, expiry/revocation, usage limit and unavailable cloud; assert zero accidental paid-API calls. Verify cloud credentials never enter local/classifier requests and unavailable-local requests remain denied in local-only mode.
5. **Qualify one bounded real conversation.** After implementation and consent, retrieve the correct account-specific/native catalog, complete an incremental stream, execute a real client-owned coding tool with its matching result, pass an independent coding check, and complete a follow-up with preserved affinity. A model list, login badge, HTTP `200` or echoed answer cannot substitute for this workflow.
6. **Qualify failure and recovery.** Exercise selected-transport continuation, cancellation/interrupted streams, model/policy denial, token renewal and confirmed revocation/account switching. Record ambiguous results as unknown; do not replay a possibly started inference or change billing to manufacture success. Keep retry/time/concurrency bounds explicit.
7. **Qualify installation/restoration separately.** Run the actual CLI and desktop/plugin surface selected for release. Confirm effective provider configuration under its real precedence, preserve client permissions and user edits, disconnect only owned resources, and report retained restoration conflicts. Managed requirements must remain under their legitimate owner.
8. **Publish redacted evidence and a narrow support statement.** Record exact versions, route/credential *kind*, model, completion/tool/check outcomes and negative-case results, without credential values, identifying account data or private paths. Release only the proven combination; broader clients, models, regions or account classes require separate qualification.

The transport/tool checks follow [gateway compatibility and its qualification checklist](https://learn.chatgpt.com/docs/enterprise/gateway-compatibility); native prerequisites follow [native gateway setup](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway); consent/error checks follow [registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) and [recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery). The no-new-agent-loop and recoverable-setup requirements remain [Hormuz scope](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/docs/ROUTER_SCOPE.md) and [connected-client ownership](https://github.com/Xpounder-com/hormuz/blob/fb5084cb235fd9e9e82f501ce5af03c956432bf5/docs/decisions/0017-connected-client-lifetime.md).

Research resolves which documented paths exist and why current generic transport does not qualify them. **The deployment choice, actual user eligibility/consent, implementation and native qualification remain open gates.** This note authorizes none of those actions and does not close the customer-local router epic.
