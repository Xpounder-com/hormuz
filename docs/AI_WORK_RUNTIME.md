# AI work runtime

The opt-in AI-work runtime joins covered gateway activity to actor-owned jobs,
enforces customer spending limits before egress, and selects eligible routes
using customer-local observational evidence. It is additive to the existing
gateway usage, policy, finance, attribution, and connector owners. Its ledger is
not a provider invoice, a global model leaderboard, or a universal numerical
unit of problem-solving.

## Identity and ownership

`WorkRuntime` accepts the existing `config.Identity`. Every work-item read,
observation, attempt, action, and cache operation checks both `organization_id`
and `actor_id`. A work ID is not authority. Ordinary reports show owned jobs.
`report(identity, administrator=True)` shows only that identity's organization;
the HTTP layer must authorize this explicit operator operation. It must also
authorize workspace/repository plan administration before calling `set_plan`.
Members may only change plans/actions for their owned jobs through the HTTP API.

Repository, context revision, source reference and optional display title are
explicitly supplied bounded metadata. Declared task types take precedence. When
the task type is absent, `bind_request_context` uses fixed, bounded rules on the
latest sanitized user instruction to identify conservative task characteristics.
It records only labels, size buckets and capability flags, with
`task_origin=inferred_characteristics`; ambiguous input remains unknown and uses
the approved baseline. No model call or prompt content is retained. A title is a customer label,
never generated by reading a prompt. Prompts, responses, patches, and tool output
are not written to the work ledger. The opaque `unattributed` repository/task
cohort is reported honestly and never used for adaptive model learning.

## Domain interface

```python
runtime = WorkRuntime(database_path, config=config, cache_enabled=False,
                      minimum_samples=5)
work = runtime.create_work(identity, "organization/repository",
                           title="CI repair", task_type="ci-repair",
                           context_revision="immutable-context-version")
runtime.set_plan(identity.organization_id, "job", work["work_id"],
                 budget_microusd=5_000_000, objective="speed", expected_version=0)
choice = runtime.choose_route(identity, work["work_id"], approved_model_routes,
                              baseline_route, request_value)
reservation = runtime.reserve(
    identity, work["work_id"], request_id, selected_model_route, "openai",
    max_cost_microusd=bounded_request_upper_estimate, reason=choice["reason"],
    logical_request_id=logical_request_id,
    request_pattern=runtime.pattern_for_request(redacted_request),
    request_shape=runtime.shape_for_request(redacted_request),
)
# Never dispatch an idempotent replay a second time.
runtime.settle(identity, request_id, cost_microusd=observed_gateway_cost,
               status="succeeded", latency_ms=observed_attempt_latency)
# Record the actual workflow signal and its source. HTTP success does not do this.
runtime.observe(identity, work["work_id"], "completed", source="agent",
                reference=workflow_delivery_id)
runtime.close()
```

The main operations return closed JSON-compatible metadata dictionaries.
`WorkRuntimeError.reason` is a fixed classification and `.status` supplies the
HTTP status. Work-not-found is 404 for both absent and unowned work; plan/request
conflicts are 409; a spending refusal is 402; unavailable storage is 503.
The domain does not accept external tenant/actor authority from request bodies.

`get_work` and `list_work` return work state, current plans, accounting, submitted
observations, and the latest 100 attempt records with `attempts_truncated`.
`report` returns `hormuz.ai-work-state` version 1, works, plans, totals, as-of time,
coverage, report scope, and cache contract. Work records distinguish active,
paused, completed, canceled, and unknown. Outcome evidence remains unknown
without an explicit observation. References provide idempotent observation
delivery; changed or independent observations append rather than rewrite history.

## Spending and continuation

Plans use `workspace`, `repository`, or `job` scope. A workspace scope ID must be
the organization ID. Workspace and repository plans cover the current UTC month;
job plans cover the whole job lifetime. `None` means uncapped, while zero blocks
positive-cost reservations. More-specific plans choose the routing objective,
but every ancestor spending cap applies. Objective names are `cost`, `speed`, and
`quality`; UI aliases cost-first/speed-first/outcome-first are accepted.

SQLite `BEGIN IMMEDIATE` serializes applicable limit checks and reservation
insertion across threads and runtime instances. Pending and unknown requests
retain their full conservative upper estimates. Terminal cost evidence settles
a hold once, and identical settlement is idempotent. Missing usage becomes an
unknown hold rather than invented free inference. A subsequent explicit known
settlement can resolve that hold. A provider charge above its reservation is
recorded with `reservation_exceeded`; it cannot be retroactively prevented and
remains visible to the next budget check.

The caller must supply a defensible upper estimate, including model input,
maximum output and potential cache write rates. Unsupported provider-resolved
inputs and unbounded output must be rejected by the gateway before dispatch.
AI Work's configured token rates cover qualified standard processing. Explicit
unqualified processing tiers, fast inference and geography overrides are
refused before routing, answer reuse or provider dispatch. Standard service
tier selection is pinned using the provider's request enum. Unexpected pricing
dimensions in a provider response retain the work reservation as unknown and
prevent answer-cache insertion. A delivered response can still establish
continuation affinity; delivery and charge certainty remain separate.

Operators must qualify the configured rates against the actual account,
endpoint, model/context size, geography defaults and cache-write duration.
Hormuz does not change a customer's residency policy or discover contractual
prices from request text. The default geography remains the approved account's
setting; its price envelope is a live qualification requirement. Customer speed
preferences choose among qualified model routes and do not authorize an
unpriced processing tier.
An observed alternate geography still leaves the work charge unknown: configured
token rates alone do not certify a geography-specific pricing profile.
Provider request and observed metadata follow the documented
[OpenAI service tiers](https://developers.openai.com/api/docs/guides/fast-mode),
[Anthropic service tiers](https://platform.claude.com/docs/en/api/service-tiers),
[speed modes](https://platform.claude.com/docs/en/build-with-claude/fast-mode) and
[geography controls](https://platform.claude.com/docs/en/manage-claude/data-residency).
The existing provider attempt owner and this work ledger have separate stores;
integration releases only known unstarted holds on a work-ledger refusal.
Crash uncertainty leaves conservative holds and never automatically replays a
provider request.

`act` supports pause, resume, stop and approve_budget. The latter atomically
changes an owned job plan and resumes it, with optional plan-version comparison.
It cannot enlarge a workspace/repository cap. These actions control subsequent
requests; they do not revoke provider work already in flight. The integration
must present or propagate its pause/refusal to the calling agent.
Passive correction, reopen and unknown observations preserve a customer pause
or stop; only an explicit continuation action restores admission.

Reports distinguish committed, pending and uncertain amounts. Remaining amount
includes all three. The monthly forecast is a linear projection of committed
gateway estimates, excludes in-flight holds, and is unavailable with unresolved
uncertainty. It is not a workload-aware prediction or final monthly bill.
Coverage is `gateway_captured_work_requests_only`; bypassed traffic and unrelated
subscriptions are outside this accounting.

Durable metadata has no cumulative lifetime row ceiling. Retained completed work
from prior months does not exhaust a future month's work admission or request
allowance. SQLite disk capacity, free space, backup consistency and retention
remain operator responsibilities. Operators must monitor those resources and
archive or retain history under an explicit policy; memory, report and benchmark
bounds are separate from durable retention. History supporting active job limits,
the current month's shared limits or unresolved holds must remain intact. Deleting
that history to recover space or reset an allowance is not an approved operation.
Storage failure refuses new admission; it never silently discards budget evidence.

State reports show the latest 100 jobs, at most five recent attempts and five
recent observations per job, and at most 100 applicable plans. The `display`
metadata states these bounds and whether the view is truncated. Aggregate cost,
job and completion totals cover the entire authorized scope. The owned job
detail endpoint returns up to 100 attempts and 1000 recent observations; limits
and truncation are explicit there too.

## Customer-local learning and quick selection

The benchmark groups observed work by tenant, repository, task type, protocol,
versioned completion condition, characteristic/context signature, request
capability shape and a fingerprint of the configured model/version/rates
and provider origin.
Every model attempt, retry, failure and cache hit stays inside its work episode.
Mixed-model, mixed-capability, unsettled, cached-only, unobserved, and incomparable
episodes do not supply model-success samples. The background builder considers
at most 1000 recent observed episodes with at most 10,000 complete attempt rows.
Episodes with more than 1000 attempts are excluded rather than partially scored.
Eligible episodes must include an attempt in the last 90 days. Reopened/corrected
work contributes rework evidence; it is not silently
counted as a clean completed task. Submitted workflow/agent/operator observations
remain their stated source, without being promoted to independently verified
correctness.

Normal route selection reads a bounded memory snapshot. A miss/stale snapshot
queues bounded background computation and uses the approved baseline while it
refreshes. Observations and settlements immediately retire comparable snapshots
and queue fresh evidence after the ledger transaction commits. Generation checks
prevent an older background build from restoring evidence preceding a correction.
Snapshots live for at most 30 seconds; `refresh_benchmark` permits
explicit provider-free replay outside request routing. No prompt-classifying
model call or network call occurs in selection. A minimum sample count is a
cold-start guard, not a statistical proof or universal quality threshold.

Alternative cold starts can collect evidence from actual incoming work when
`ai_work.exploration_aliases`, `exploration_rate_percent` (1–20), and a positive
`exploration_max_cost_microusd` monthly workspace allowance are configured.
Exploration is off by default and can be enabled by configuration or an explicit
plan override. An explicit parent-plan opt-out cannot be overridden by a child
plan. A plan override cannot grant unapproved aliases or a larger
allowance. Only attributed, interactive, stateless initial requests are eligible;
tools, continuation, machine repeats and jobs with prior attempts are excluded.
The baseline must already have the configured minimum observed episodes.
Selection allocates at most the rounded-up configured fraction of admitted work,
reserves the quoted maximum against the monthly exploration allowance atomically,
and checks every parent budget. The ordinary reservation still performs atomic
budget admission. One approved alternative receives the original request; no
duplicate provider or tool action is executed. Unused/unknown allocations remain
conservative holds for that month. An experimental selection is explicitly labeled
and does not claim known quality.

Cost-first selects lower observed episode cost; speed-first selects lower summed
observed gateway wall latency when completely measured, otherwise measured
provider latency, requiring complete timing. Both require completion
and rework rates no worse than the approved baseline in the comparable sample.
Outcome-first prefers higher observed completion and less rework. All results
are labeled observational. Provider-attempt time and elapsed workflow-completion
time are reported separately; summed provider latency is not human productivity
or end-to-end delivery time. No-repeat behavior never establishes correctness.

The gateway filters policy-approved candidates first. The selector also retains
same-protocol eligibility. Opaque provider state and nested tool continuation
pin the prior model, or fail closed if it is no longer eligible. Initial requests
with tools can adapt only among explicit operator-declared
`ai_work.tool_capable_aliases`, with matching observed capability shapes; otherwise
they retain the approved baseline. This declaration is a capability contract
requiring actual integration qualification. It does not make arbitrary models
compatible with every agent or tool schema.

`pattern_for_request` creates an HMAC of the exact canonical redacted request
excluding its model field. The random key exists only in this process. Only a
bounded opaque digest is persisted, and it is never returned by reports.
Exact recurrence within one owned job and 15 minutes is marked
`possible_exact_recurrence_not_quality`. Known automatic retries, `retry_of`
attempts, and explicitly legitimate iterations are excluded. Similarity,
semantic reask inference, automatic task completion and model correctness are
not inferred. Correction observations invalidate cached responses and reset
route affinity. Restart changes the HMAC key, deliberately preventing continued
request-content fingerprint linkage across restarts.

`recurrence_guard` allows the first exact answer-cache replay. After two recent
consecutive interactive exact attempts including at least one cache replay, it atomically
advances the job/context cache generation and records `possible_repeat_not_quality`.
The bypass resets its detection watermark, has a 60-second cooldown and uses the same owned-job, context and
15-minute recurrence window. Declared retries, polling, scheduling, history,
legitimate iterations and provider/tool continuation are excluded. This policy
does not create a correction observation or infer correctness. In-flight responses
from the preceding generation cannot reseed the cache.

## Exact answer-cache contract

Answer reuse is separately opt-in (`cache_enabled=false` by default). It is
bounded process memory, with at most 128 entries/8 MiB by default and 1 MiB per
answer. No cache bodies, prompts or cache-request digests are written to SQLite.
Restart clears content. TTL is explicit and bounded to one hour (default 60 s).

`cache_get(identity, work_id, request_value, model_route, policy_version)` returns
None or a response record containing immutable body bytes, status code,
allowlisted Content-Type, source, opaque cache ID and expiry. `cache_put` accepts
a body and optional TTL/headers. Only HTTP 200 complete text responses are
eligible; the gateway additionally validates provider-specific terminal/output
shapes before insertion.

The cache key binds tenant, actor, work ID, caller-declared context revision,
versioned completion condition and characteristic/context signature,
durable invalidation generation, configured model fingerprint, policy version,
API endpoint (added by the gateway), and the entire canonical request. Parameters
must match exactly. There is no semantic cache. A context revision is mandatory;
its freshness is the application's responsibility. Temperature must explicitly
be zero. Streaming, tools, tool history, provider state references, externally
resolved files/prompts, non-text modalities, storage and background execution
bypass reuse. Authorization is rechecked before access. Correction/reopening,
stop, explicit invalidation, TTL, route/policy/context drift and restart prevent
hits. Hits consume zero new provider cost and are separate attempt records,
without establishing work completion or additional quality samples.

The gateway captures `cache_generation(identity, work_id)` before dispatch and
passes it as `cache_put(..., expected_generation=...)`. An answer from an older
generation cannot repopulate the cache after a correction or reopen. Insertion
without an explicit dispatch generation is refused. Returned
entries include their generation, which cache replay passes to
`reserve(..., expected_cache_generation=...)` for atomic admission validation.
Insertion rechecks the generation under the same write lock as correction.

## Timing, reconciliation and forecasts

`record_timing` records measured provider and total gateway intervals, computes
their overhead difference, and accepts only bounded fixed stage labels. Missing
measurements remain null; completion elapsed time remains a separate workflow
clock. Transport measurements use `provider_transport_blocking_time`, the observed
upstream open/read intervals, and gateway wall time through work-ledger settlement;
they do not claim provider GPU execution time. Older externally supplied intervals
retain their legacy/external basis. Timing observations do not invent compute prices: overhead monetary cost
and unallocated subscription/platform charges remain explicitly outside the
covered provider-cost total.

`confirm_cost` preserves the original settlement estimate and attaches a separate
amount, provider source and opaque reference. It requires an independently verified
provider-import boundary with tenant/request binding; an ordinary customer amount
or assertion cannot confer confirmation. Confirmation is idempotent, rejects
conflicting/reused references and changes covered budget consumption to the verified
amount. A verified receipt does not establish invoice finality. Financial
reconciliation of an unknown attempt releases its cost hold without inventing a
successful outcome or supplying a model-success sample.

Organization reports can also display existing account-bound provider aggregate
cost evidence through `work_provider_costs`. Both the work administrator boundary
and an exact configured `portfolio_admin` principal are required. The existing
finance repository rechecks source/account binding, period and audit provenance.
It returns provider-reported amounts, covered gateway estimates, missing buckets,
matching limitations and the collection origin for complete UTC days in the
current month. Provider credentials are not resolved and no provider collection
occurs on a report read. Customer-file imports retain their unverified source
label. These account aggregates are never distributed to individual jobs or
requests and never acquire invoice finality from a configured binding.

Monthly plans expose a point run-rate estimate and separate low/high observed-day
scenarios after at least three complete observed activity days. These are scenarios,
not statistical confidence bounds or a guaranteed invoice. Coverage, observed-day
count and fixed uncertainty reasons are returned. Holds remain separate and
unresolved provider costs suppress the point estimate. Forecasts are local to the
covered gateway traffic and do not imply unobserved customer work is included.

## Verification

Run `python tools/ai_work_benchmark.py --output /tmp/ai-work-benchmark.json`
for a reproducible, provider-free local check with 10,000 synthetic jobs and
99,990 attempt records. It measures 500 snapshot route selections, a background
benchmark build and a bounded report, identifies its source files by digest,
and checks a 30 ms local routing p95 target. The checked-in measurement is
`docs/evidence/ai-work-functional/local-benchmark.json`. This is local metadata
mechanics evidence; it does not establish production load capacity, provider
latency, customer savings or task correctness.

The existing recommendation/runtime predecessor plans remain frozen. The
digest-pinned `ai-work-source-successor-v1.json` authorizes only reversible
additions for the separate work/billing inventory, source-kit includes and their
inventory checks. Verification removes those exact additions and still compares
the original source SHA; changing legacy sources, wire contracts, schemas,
fixtures or the authorization document fails closed. Workspace/work CSS enters
the wheel through explicit MANIFEST includes, preserving the legacy package-data
declaration and its predecessor guards. The recorded local CSS wheel check
proves inclusion only; it is separate from a locked release build.

Run `python -m unittest tests.test_work_runtime -v` in the qualified project
environment. The tests exercise tenant/owner isolation, concurrent instances,
durable unknown holds, parent limits and continuation, compare-and-set,
idempotency, recurrence exclusions, objective selection, model/schema drift,
session affinity, snapshot-only request routing, exact cache isolation,
correction/TTL/restart invalidation, bounds and content-free persistence.

No focused unit suite establishes fresh-customer onboarding, provider invoice
reconciliation, live-model task quality, compatibility with every coding agent,
payment readiness, multi-region storage, or production distribution. The runtime
is SQLite/single-node; this path must not be enabled on ephemeral filesystem or
represented as a shared PostgreSQL service without a separate storage contract.
